# multi-user/04 — 审阅工作流状态机

## Question

审阅最低要求已定：审阅者能看能改。本工单定状态机：

- 状态单位 = (Clip, Task type)（随工单 03 决策）。状态集合与迁移：如 分配中 → 标注中 → 待审 → 审阅中 → 已审；驳回/打回要不要（最低要求里没有，但审阅者改完标注员要不要知情？）。
- 审阅者的改动如何记录：直接改在原标签上？要不要区分"标注员标的"与"审阅者改的"（审计/追溯需求）？
- 标注员何时看到审阅结果；已审 Clip 能否再改、由谁改。
- 状态迁移权限：谁能把 Clip 从"标注中"推到"待审"（标注员自己交？管理员交？）。

## Answer

五态状态机，单位 = (Clip, Task type)；**审阅是可选阶段，可跳过**：

```
未分配 → 标注中 → 待审 → 审阅中 → 完成
         ｜
         └──→ 完成（跳过审阅）
```

- **标注中 → 待审**：标注员自己交审，管理员可代交；交审后标注员锁定，可**撤回**退回标注中。
- **待审 → 审阅中**：管理员指派审阅人，机制照抄标注指派（手动 + 按持有量均衡自动）；**审阅人 ≠ 该条目标注员**。没派上人的条目停在待审排队，看板可见积压。
- **审阅中 → 完成**：审阅者改完通过，条目记 reviewed-by + 时间。
- **标注中 → 完成（跳过审阅）**：标注员或管理员直接标完即完成；reviewed-by 为空 = 未经审阅。终态统一叫**完成**，不叫已审；"审后完成 / 免审完成"由 reviewed-by 有无区分，不设两个终态。
- **打回**：小问题审阅者直接改；大问题打回 → 标注中 + 一条短备注（条目级文本，无评论楼层），标注员可见。已完成的条目管理员/审阅者可送回待审补审或退回标注中重开。
- **留痕**：条目级 reviewed-by 元数据；帧级不记作者。

下游同步：05 的条目记录需承载状态 + reviewed-by + 备注；08 的标注员侧需交审/标完成两个动作，审阅者侧的队列即"审阅中"条目列表。

### 修订（2026-09-08，用户复核后改模型）

上一版"标注中 → 完成（跳过审阅）"分支**作废**。改为：

```
未分配 → 标注中 → 已提交 → 审阅中 → 完成
                    │
                    └→ 下游直接取用（不改状态，记已交付标记）
```

- **提交不分支**：标注中 → **已提交**（原"待审"改名，含义 = 标注完、未审）。交出即锁定，可撤回，管理员可代交——不变。
- **完成 = 审阅通过**，唯一终态：已提交 → 审阅中（管理员指派，审阅人≠标注员）→ 完成，reviewed-by 必有值。不再有免审终态。
- **取用**：任何已提交条目可被下游直接使用，不改变流程状态；**留痕**——条目记已交付标记（含时间），管理员/审阅者可设置，看板可见。取用后条目仍可继续走审阅。
- 其余不变：打回 + 备注（条目级短文本）、撤回、留痕只到条目级。

下游联动更新：05 的条目字段加已交付标记；08 的标注员出口改为提交/撤回，管理员侧加已交付标记入口。
